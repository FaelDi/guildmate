# Claude Code Review Configuration

> Automated code review configuration for GuildMate

## Repository Information

- **Name**: guildmate
- **Primary Language**: TypeScript
- **Type**: Full-stack web application (Next.js App Router)
- **Description**: A guild portal for RF Next players — guild and character registry, live
  events scored with a time-limited join code, an append-only point ledger, admin point
  auctions, and a player item store priced in diamonds
- **Database**: Supabase Postgres via Drizzle ORM
- **Auth**: Supabase Auth, server-side only
- **Deploy**: Vercel
- **Branch**: `main` — the only one. It is what Vercel deploys, and it is pushed to directly

## How to Use This Configuration

### Before starting a review

**REQUIRED**: read [CLAUDE.md](./CLAUDE.md) first — it defines the DUCK Protocol, the
testing bar, the security rules and the Rule → Service → Action architecture. Cite its
sections when flagging a deviation.

### Review approach

1. Read the documentation before making architectural recommendations.
2. Cite specific files and lines. A finding without a concrete failure scenario is noise.
3. Verify compliance with the established patterns rather than proposing new ones.
4. Rank by exploitability × blast radius. Point minting and authorization bypass first.

## Coding Standards

- **TypeScript**: `strict` + `noUncheckedIndexedAccess`. No `any`. No non-null `!` assertion
  to silence a real nullability case.
- **Security**: [OWASP Top 10](https://owasp.org/www-project-top-ten/) and
  [OWASP API Security Top 10](https://owasp.org/www-project-api-security/) — API1 (BOLA)
  above all.
- **Commits**: Conventional Commits, no AI co-author trailer.
- **Language**: English only in code, comments, logs and tests.

## Review checklist

### 1. The point economy (highest severity)

The ledger is the thing an attacker wants to corrupt. Check every diff that touches points:

- [ ] No `UPDATE` on `point_ledger.amount`, no `DELETE` from `point_ledger`, no cached
      balance column anywhere. Corrections are new delta rows.
- [ ] A new award is written `PENDING`, never `CONFIRMED`. Points become spendable only
      through the event reaching quorum. **Writing `CONFIRMED` directly mints spendable
      points — always P1.**
- [ ] The ledger write is inside the **same transaction** as the registration, bid or
      adjustment that justifies it.
- [ ] Balance reads that gate a write (`availablePoints` before a bid) happen **inside** the
      transaction, with the auction row locked (`.for('update')`). Flag any check-then-act
      gap.
- [ ] Re-scoring an event emits one delta per live registration and skips `REVERSED` ones.
- [ ] Cancelling an event reverses **every** award for it, pending and confirmed.

### 2. Authorization (OWASP API1 — BOLA/IDOR)

- [ ] Every read or mutation of a member-owned row calls `authorizeResource` in the
      **service layer**, after the row is loaded. A role check alone is a finding.
- [ ] Guild scoping is checked, not just ownership: an admin of guild A must not touch
      guild B.
- [ ] Guild-wide actions call `authorizeAdminAction`.
- [ ] Moderation calls `authorizeModeration` / `authorizeRoleChange`: strictly lower rank
      only, never self, never granting a rank at or above your own.
- [ ] An admin cannot award points to their own account **or its alts** — the check is on
      the owning user, not the character.
- [ ] The guard is present on **every** affected entry point, not only the one in the
      ticket. Grep for siblings.
- [ ] Ids arriving in `FormData` (`userId`, `characterId`, `eventId`, `listingId`) are
      treated as attacker-controlled and re-authorized server-side.

### 3. The Supabase boundary

- [ ] **No `NEXT_PUBLIC_SUPABASE_*` variable is introduced.** This is a hard rule; adding
      one is a security regression.
- [ ] `src/db/*` and `src/lib/supabase*.ts` still import `server-only`.
- [ ] No client component (`'use client'`) imports from `@/db`, `@/services/*` or
      `@/lib/supabase*`.
- [ ] `SUPABASE_SERVICE_ROLE_KEY` is only used behind a route that has already
      authenticated **and** authorized the caller. It bypasses RLS.
- [ ] The storage proxy stays deny-by-default: object keys are validated with
      `parseObjectKey`, the caller never chooses the key on upload.

### 4. Architecture

- [ ] A new domain rule is a **pure function in `src/lib/rules.ts`** returning a
      `RuleResult` — not an inline `if` in a service, an action or a page.
- [ ] `rules.ts` stays pure: no I/O, no `new Date()` inside (time is injected as `now`).
- [ ] Services do not re-decide a rule; they `unwrap()` it.
- [ ] Actions contain no business logic: authenticate, gather input, call the service,
      return `ActionResult`.
- [ ] Errors surface through `AppError` / `runAction`. No raw exception message reaches
      the client.

### 5. Tests

- [ ] New or changed rules have tests, and at least one **would fail without the change**.
- [ ] Boundaries are covered: the instant a code expires, quorum reached exactly, a bid one
      point below the minimum, a restriction expiring exactly now.
- [ ] Denial paths are covered, not just the happy path.
- [ ] `npm test` passes with zero failures (read the output, not just the exit code).

### 6. Build and schema

- [ ] `npm run build` succeeds — this is the Vercel deploy gate; a type error is a broken
      production deploy.
- [ ] A schema change ships with its generated migration under `drizzle/`, and the SQL has
      been read and is not destructive.
- [ ] A new env var is in `.env.example` and `docs/DEPLOYMENT.md`.

### 7. Data exposure

- [ ] No password, event code, token or Supabase key in a log, an error message, or the
      audit log (which must go through `redact()`).
- [ ] A resource the caller may not see returns the same response as one that does not
      exist — no existence oracle.
- [ ] Sign-in keeps one generic failure message and comparable timing across unknown
      email, wrong password and banned account.
- [ ] Raw IPs and user agents are stored only as `fingerprint()` hashes.

### 8. Performance

- [ ] Every list query has a `LIMIT`.
- [ ] No N+1 introduced in a loop over rows.
- [ ] A new filter on a hot path comes with its index in the same change.
- [ ] Balances are aggregated in SQL, not by loading the ledger into memory.

## Severity guidance

| Severity | Examples |
|---|---|
| **P1 — block** | Points mintable; a missing ownership check; an admin self-award path; a secret reaching the client or a log; `npm run build` failing |
| **P2 — fix before merge** | A rule implemented inline instead of in `rules.ts`; a missing test on a changed rule; a check-then-act race; a schema change without its migration |
| **P3 — follow-up ticket** | Naming, duplication, a missing index on a cold path, docs drift |

## Known incidents this checklist came from

- **The scrypt `maxmem` bug.** `maxmem` was budgeted at exactly `128 * N * r`, the
  theoretical working-set size. OpenSSL needs headroom on top of that, so every password
  hash threw `memory limit exceeded`. It was caught only because a test called the real
  hashing function rather than mocking it. **Lesson: test crypto against the real
  primitive.**
- **Balance reads outside the transaction.** An early draft of `placeBid` read the balance
  before opening the transaction, so two concurrent bids could both pass the funds check.
  Fixed by moving the read inside and locking the auction row. **Lesson: any precondition a
  write depends on must be read under the same lock.**
